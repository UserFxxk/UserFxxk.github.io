AUTHORIZED SECURITY ASSESSMENT • COORDINATED DISCLOSURE

Root-Cause Analysis: Unauthenticated Data Exposure & Input Boundary Flaws in an Agricultural Ration Solver API

Author: Fata Fatikhul Karim • Target Stack: Express.js / REST API • Scope: Authorized Testing & Coordinated Maintainer Disclosure

1. Context & Threat Model

Agricultural ration formulation platforms compute optimal livestock feed mixtures based on biological constraints such as body weight (BB), Dry Matter percentage (DM%), crude protein, and mineral requirements. During an authorized security review of a web-based ration solver, I evaluated the system across two intersecting threat surfaces:

  • Access Control & Multi-Tenant Privacy: Whether calculation histories and custom feed definitions were properly scoped to authenticated users.
  • Domain-Math & Input Boundary Integrity: Whether the backend API enforced biological and mathematical bounds before passing user inputs to the linear solver and database layer.

2. Root-Cause Analysis (Vulnerable Code Patterns)

The assessment uncovered 8 vulnerabilities (3 High, 4 Medium, 1 Low). Below are the three high-severity root causes: 

// ❌ VULNERABLE PATTERN 1: Unauthenticated History Endpoint (Broken Access Control)
app.get('/api/history', async (req, res) => {
  // Missing authentication middleware and tenant ownership filter!
  // Exposed 38 historical ration records belonging to other users.
  const history = await db.history.findAll();
  return res.status(200).json(history);
});

// ❌ VULNERABLE PATTERN 2: Unvalidated Numeric Mutation on POST /api/feeds
app.post('/api/feeds', async (req, res) => {
  // Directly trusts req.body without schema or numeric boundary checks.
  // Accepting negative Dry Matter (e.g., DM: -500%) caused floating-point
  // divergence (2.3e+289 kg) in persisted solver outputs.
  const feed = await db.feeds.create(req.body);
  return res.status(200).json(feed);
});

3. Business & Operational Impact

  • Tenant Data Leakage (High): Any unauthenticated visitor querying GET /api/history could read proprietary feed formulation records of other users.
  • Shared Catalog & Solver Integrity (High): Read-only inspection of the history endpoint revealed pre-existing corrupted float records (2.3e+289 kg) and invalid catalog entries (e.g., non-nutritional strings under the Mineral category). Two controlled verification records were logged by UUID (4e856b17..., a030ba7f...) and immediately disclosed to the maintainer for cleanup.
  • Client Thread Denial-of-Service (High): Empty HTML min/max attributes allowed zero or negative livestock body-weight inputs to enter the solver loop, freezing the client tab.

4. Defensive Remediation & Regression Unit Tests

To remediate these flaws without breaking legitimate formulation workflows, I provided the engineering maintainer with a defense-in-depth patch combining Zod schema validation, ownership-scoped authorization middleware, and automated Jest regression tests: 

// ✅ PATCHED IMPLEMENTATION: Strict Domain-Bound Schema + Ownership Scoping
import { z } from 'zod';
import helmet from 'helmet';

app.disable('x-powered-by');
app.use(helmet());

const FeedPayloadSchema = z.object({
  name: z.string().trim().min(2).max(80),
  category: z.enum(['Forage', 'Concentrate', 'Mineral', 'Vitamin']),
  dryMatterPct: z.number().min(0.5).max(100),   // Biological DM bound: 0.5% - 100%
  bodyWeightKg: z.number().min(1.0).max(2500)   // Prevents 0/negative solver hang & overflow
});

app.post('/api/feeds', requireAuth, async (req, res) => {
  const parsed = FeedPayloadSchema.safeParse(req.body);
  if (!parsed.success) {
    return res.status(400).json({ error: 'Invalid feed parameters', details: parsed.error.issues });
  }
  const feed = await db.feeds.create({ ...parsed.data, createdBy: req.user.id });
  return res.status(201).json(feed);
});

app.get('/api/history', requireAuth, async (req, res) => {
  const records = await db.history.findMany({ where: { userId: req.user.id } });
  return res.status(200).json(records);
});
