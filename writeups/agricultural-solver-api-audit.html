Root-Cause Analysis: Unauthenticated Data Exposure & Input Boundary Flaws in an Agricultural Ration Solver API

Author: Fata Fatikhul Karim • Target Stack: Express.js / REST API • Findings: 8 Total (2 High, 4 Medium, 1 Low, 1 Informational)

Authorization & Publication Approval: This assessment was conducted under direct authorization from the system owner on October 9, 2026. All actionable vulnerabilities were patched in production and verified via re-testing by October 14, 2026. Published with explicit maintainer permission granted on October 15, 2026, with proprietary hostname and tenant identifiers redacted.

1. Context & Threat Model

Agricultural ration formulation platforms compute optimal livestock feed mixtures based on biological constraints such as body weight (BB), Dry Matter percentage (DM%), crude protein, and mineral requirements. During an owner-authorized security review of a web-based ration solver, I evaluated the system across two intersecting threat surfaces:

  • Access Control & Multi-Tenant Privacy (CWE-306 / OWASP API1 & API5): Whether calculation histories and custom feed definitions were properly gated by authentication and scoped to session owners.
  • Domain-Math & Input Boundary Integrity (CWE-20 / CWE-400): Whether the backend API enforced biological and mathematical bounds before passing user inputs to the linear solver and database layer.

4. Defensive Remediation & Regression Unit Tests

// ✅ PATCHED IMPLEMENTATION: Strict Domain-Bound Schema (Zod) + Authentication Middleware
import { z } from 'zod';
import helmet from 'helmet';
import cors from 'cors';

app.disable('x-powered-by');
app.use(helmet());
app.use(cors({ origin: ['https://app.authorized-domain.example'], methods: ['GET', 'POST'] }));

const FeedPayloadSchema = z.object({
  name: z.string().trim().min(2).max(80),
  category: z.enum(['Forage', 'Concentrate', 'Mineral', 'Vitamin']),
  dryMatterPct: z.number().min(0.5).max(100),   // Enforces biological DM bound (0.5% - 100%)
  bodyWeightKg: z.number().min(1.0).max(2500)   // Prevents BB <= 0 solver hang & float overflow
});

app.post('/api/feeds', requireAuth, async (req, res) => {
  const parsed = FeedPayloadSchema.safeParse(req.body);
  if (!parsed.success) {
    return res.status(400).json({ error: 'Invalid feed parameters', details: parsed.error.issues });
  }
  const feed = await db.feeds.create({ ...parsed.data, createdBy: req.user.id });
  return res.status(201).json(feed);
});

app.get('/api/history', requireAuth, async (req, res) => {
  const records = await db.history.findMany({ where: { userId: req.user.id } });
  return res.status(200).json(records);
});

5. Conclusion & Engineering Takeaways

This assessment demonstrates three critical lessons for full-stack and security engineers:

  • Domain-Aware Input Validation: Generic type checks (e.g., typeof dm === 'number') are insufficient for scientific or financial solvers. Server-side schemas must enforce domain-specific invariants (`0.5 <= dryMatterPct <= 100` and `1 <= bodyWeightKg <= 2500`).
  • Default-Deny Authentication & Tenant Scoping: Read endpoints returning historical calculations (GET /api/history) and shared catalog mutations (POST /api/feeds) must enforce authentication middleware and tenant ownership filters by default.
  • False-Positive Triage in Security Reviews: Initial observation of SameSite=None on the __cf_bm cookie (`SOLVER-06`) was properly triaged and downgraded to Informational (`0.0 INFO`) upon confirming it is managed by Cloudflare Bot Management rather than the application's session layer.
